## 这是什么

一份**给 AI 读的审查剧本**。把本仓库给你的桌面端 AI，说一句"审查一下我的文档，哪些能删能合并"，它会按 21 条判定式把你的 Markdown 仓过一遍，输出一张**可执行清单**——而不是上来就删你的文件。

## 解决什么问题

| 症状 | 判定式 | 处置 |
|------|--------|------|
| 同一件事三个文件各写一遍 | 单一事实来源 | 后者改指针 |
| 早期需求稿、旧版本堆在根目录 | 旧版清退 | 删（先查孤本） |
| 内容放错了仓 | 放对层 | 下沉/上交 |
| 同一数据两处维护，改一处漏一处 | 双写消除 | 单点 + 自动带入 |
| 长篇解释，其实一句就能说清 | 判定式短句 | 压成要点表 |
| 题库/台账当文档存，AI 逐行读 | 数据当文档（脚本 S2） | 转 JSON/CSV |
| 「工具/资料/其他」目录里又套了一层 | 命名笼统=变相加层 | 命名具体化或解散 |
| 台账里堆了一堆日期进度 | 台账不搬流水 | 流水回项目仓 |
| 规范里夹着命令对照表、安装步骤 | 操作细节不属于规范 | 外链或移交项目仓 |
| 机制停了功能废了，但历史有参考价值 | 冻结不删 | 冻结归档：不删历史、留导航 |

## 为什么这么厚

文档冗余的形态比想象中多，**漏掉一类就等于白审一次**。所以本 skill 故意不做成三行清单：

- **8 条核心判定式**——覆盖主要冗余形态
- **13 类补漏判定式**——实战中最常漏掉的冗余源（命名、流水、头注、操作细节、孤儿、冻结、旧措辞……）
- **11 条防呆清单**——孤本三查、改名三件套、别顺手剪掉、别过度执行……
- **14 个真实反面案例**——踩过的坑比抽象原则好记

## 怎么用（三步）

1. 把这个仓库放到你的 AI 能读到的地方（或直接把 `SKILL.md` 全文复制）
2. 对**桌面端 AI**（豆包桌面端 / Kimi / WorkBuddy / Claude Code / OpenClaw…，任何能读写本地文件的都可以）说：
   > "按 kb-slim-audit 审查 `你的文档目录` 下的 MD，告诉我哪些能删、能合并、能压缩"
3. AI 输出清单 → **你逐条拍板** → 让它执行或自己动手

> ⚠️ **只用网页版的不适用**——网页版不能读写本地文件，扫不了你的目录。

## 输出长什么样

```
### 待拍板
- [并] 立项-初稿.md + 立项-工单版.md：同一立项两份 → 合并为立项与定位.md
- [压] README.md：与总览文档双写简介 → README 只留导航
- [删] 题库-新增724.md：数据已导入系统 + 已转 JSON → 删除

### 查过不动（防误删备忘）
- 骨架 README vs README模板：看似重复，实为职责不同
```

## 为什么"查过不动"也要记录

不记录 = 下次审查重复劳动 + 下个 AI 可能误删。**查过确认没问题的，和有问题的同样重要。**

## 设计原则

- **审查归 AI，拍板归人**——AI 只出清单，不擅自动手
- **先机检后人工**——脚本筛规模，人只判语义
- **孤本保护**——删之前全库 grep，没副本的压缩不删
- **断链比冗余更伤**——删章节前先查下游引用
